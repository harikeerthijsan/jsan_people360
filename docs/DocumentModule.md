# Document Management & Digital Document Vault

Status: **complete (Phase 5)**.

The vault is a shared platform service rather than an employee-only feature.
Every document has a polymorphic owner (`employee`, `candidate`, `organization`
or `user`), a configurable category and type, review metadata, expiry tracking,
and one or more immutable file versions. Each owner type is verified against its
own table, and resolves to a name and reference code on read — a bare UUID is
unusable in a list.

Preboarding links straight here with `?owner_type=candidate&owner_id=…`, so the
upload form arrives with the candidate already chosen.

The two person-shaped owner types — `employee` and `user` — are narrowed by
reporting line, so a Manager reaches their direct reports' paperwork and nobody
else's. Both are narrowed, because the vault files against either and scoping one
alone would leave the same person's documents readable through the other.
`organization` and `candidate` documents are deliberately **not** narrowed: a
policy has no reporting line, and hiding the handbook from everybody who is not
their own manager would be a bug rather than a control. See
[`RBACModule.md`](RBACModule.md#team-scoping--whose-records-not-just-which-endpoint).

## Capabilities

- Configurable document categories and category-scoped document types, managed
  in the UI with the full lifecycle: create, edit, deactivate and archive.
- PDF, JPEG and PNG uploads with client feedback and server-side signature validation.
- Configurable maximum size and storage root.
- Append-only versions with SHA-256 duplicate-content rejection.
- Authenticated image/PDF preview and downloads for current or historic versions.
- Uploaded, under-review, approved and rejected workflow states.
- Derived valid, expiring-soon (30 days), and expired states.
- Metadata editing — name, classification and expiry. The file is only ever
  changed by uploading a version.
- Search, pagination, sorting, owner, category, type, status, expiry and
  upload-date filters. The owner filter is a picker over the chosen owner type,
  and the status filter offers only the statuses a document can hold: expiry is
  derived and archiving has its own view.
- Archive and restore without deleting database records or stored files.
- Dashboard totals, status/category breakdowns and storage usage.
- Audit events for upload, version upload, update, review, preview, download, archive and restore.
- Document detail tabs for metadata, version history and audit history.

## Classification lifecycle

Deactivating a category or type withdraws it from circulation: it can no longer
be **chosen** for a new document, nor selected when re-filing an existing one.
It does not invalidate what is already filed under it — those documents stay
editable and can still receive new versions. Archiving is the stronger action
and is refused while live documents still reference the record.

## Storage and security

`StorageBackend` isolates business logic from the provider. The current local
implementation stores files below `UPLOAD_DIR`; S3, Azure Blob or MinIO can be
added by implementing the same interface. API responses never contain a
physical path or storage key.

Uploads are checked for size, extension, declared MIME type and byte signature.
Stored names are generated by the application, traversal is rejected, response
content is served with `nosniff`, and previews use a restrictive content
security policy.

## Data model

- `document_categories`: configurable grouping master.
- `document_types`: category-scoped type, expiry/sensitivity flags and optional extension narrowing.
- `documents`: logical record, owner, classification, workflow and current-version pointer.
- `document_versions`: immutable file metadata, checksum and opaque storage key.

All tables use UUID primary keys and standard audit/soft-delete fields. Alembic
revision `0005_document_vault` owns the schema.

## Frontend routes

- `/documents/dashboard` — operational summary.
- `/documents` — searchable and filterable vault.
- `/documents/upload` — drag-and-drop upload.
- `/documents/{id}` — details, preview, versions and audit history.
- `/documents/settings` — category and type administration.

## Authorization boundary

Like the existing User and Organization modules, all routes currently require
authentication. Fine-grained role-based authorization is a separate platform
roadmap item; when introduced, category/type mutation and sensitive-document
access should be assigned to appropriate HR/administrator permissions.
