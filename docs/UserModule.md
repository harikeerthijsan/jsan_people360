# User Management module

Everyone who can sign in to the platform. Accounts are created and maintained
here, and every other module — recruitment, employee records, attendance,
performance, offboarding — will reference a user rather than storing its own copy
of a person.

Status: **complete and production-ready** (Phase 3).

---

## 1. One table, three jobs

`users` is not a new table. It already existed as the authentication principal,
and this module extended it into the directory record rather than adding a
parallel "profile" table beside it.

| Job | Established by | Columns |
| --- | --- | --- |
| **Authentication principal** | Phase 1 | `email`, `hashed_password`, `failed_login_attempts`, `locked_until`, refresh-token links |
| **Directory record** | Phase 3 | `user_code`, `username`, name parts, personal contact details, the eight organizational references, `joining_date` |
| **Employee anchor** | a later phase | an `employees` row will hang off `users.id` |

One row per person, one id for other modules to reference, and no chance of the
two halves drifting apart.

Three Phase 1 columns were reused rather than duplicated:

| Spec field | Existing column |
| --- | --- |
| Official email | `email` — already the sign-in identifier |
| Mobile number | `phone_number` |
| Profile photo | `avatar_url` |

Two were removed. `full_name` became derived — storing it alongside the parts
lets the two disagree the first time someone edits only a surname. `job_title`
was free text superseded by `designation_id`, a reference to the Designation
master.

## 2. What it stores

**Identity**

| Field | Notes |
| --- | --- |
| `user_code` | `USR-000001`. Generated by the database, never editable |
| `username` | 3–50 chars, lower-cased, compared case-insensitively |
| `first_name`, `last_name` | `full_name` is derived from them |
| `email` | Official address. Also the sign-in identifier |
| `personal_email` | Optional — the address that survives offboarding |
| `phone_number`, `avatar_url`, `gender`, `date_of_birth` | Optional |

**Organizational placement** — eight optional references into the Organization
masters, plus `joining_date`:

```
Business Unit · Team
Designation   · Grade    · Location   · Employment Type
```

All eight are nullable and all use `ON DELETE RESTRICT`.

Nullable because a user can legitimately exist before the org tree does: the
bootstrap administrator is created against an empty database, and requiring a
business unit would make the first sign-in impossible.

`RESTRICT` because master records are archived, never deleted — a hard delete
that silently unassigned every user is not a recovery path.

The placement is **flat, not validated as a tree.** Nothing checks that the
chosen team sits under the chosen business unit. That check belongs in the
Employee module, where the assignment is authoritative; enforcing it here would
block the legitimate case of a user attached to a business unit and a location
and nothing else.

## 3. The staff code

`USR-000001`, `USR-000002`, … from a PostgreSQL sequence:

```sql
'USR-' || lpad(nextval('users_user_code_seq')::text, 6, '0')
```

As a column default, not application code. Two concurrent creates running
`SELECT max(...) + 1` read the same maximum and produce the same code, and the
unique index then rejects one of them for a reason the user cannot act on.

It is absent from `UserCreate` entirely, so a client cannot supply or edit one.

## 4. Two independent lifecycles

The same distinction the Organization module draws, and worth repeating because
the consequences differ for an account.

| | Meaning | Reversible | Effect |
| --- | --- | --- | --- |
| `status = active` | In normal use | — | Can sign in |
| `status = inactive` | Suspended | Yes, activate | **Cannot sign in.** Every live session is revoked |
| archived (`deleted_at` set) | Soft deleted | Yes, restore | Cannot sign in; hidden from the directory. Sessions revoked |

There is no hard delete. HR data carries retention obligations, and a row other
modules point at must not vanish.

Deactivating revokes refresh tokens immediately. Without that the existing access
token keeps working until it expires, so "deactivated" would mean "deactivated in
about fifteen minutes".

## 5. Guards

Four rules the API refuses to break, each because the alternative is a support
incident rather than an error message.

**You cannot deactivate or archive your own account.**
`409 cannot_modify_self`. You would lock yourself out of the tool you need to
undo it. The UI disables the action on your own row as well, so the reason
arrives before the click rather than after.

**The last active account cannot be deactivated or archived.**
`409 last_active_user`. Nobody could sign in, and there is no in-product way back.

**An account with linked records cannot be archived.**
`409 has_linked_records`. Today the only such link is team management — "This
user manages 2 active teams. Reassign them before archiving the account." Later
modules add their checks to the same guard, which is why the message names the
blocking relationship instead of being generic.

**An archived account cannot be edited or have its password reset.**
`409 record_archived`. Restore it first.

## 6. Identity uniqueness

Both the official email and the username are unique, enforced **twice**: in the
service so the user gets a message naming the field, and in the database so a
race cannot slip through.

| Field | Database | Why |
| --- | --- | --- |
| `email` | `UNIQUE` | Already lower-cased before it is stored |
| `username` | `UNIQUE` on `lower(username)` | A plain `UNIQUE` would accept both `J.Doe` and `j.doe` — the same handle as two accounts, which is a phishing surface |

Archived accounts **keep** their email and username. Attempting to reuse one
names the conflicting account and says it is archived, so the user restores
rather than renames:

> The username "jane.doe" is already in use by an archived account (USR-000002).
> Restore that account instead of creating a duplicate, or choose a different
> value.

Uniqueness on update is evaluated against the **resulting** record, so a partial
update cannot sidestep it.

## 7. Normalisation

Applied server-side, before any uniqueness check runs, by `Annotated` types that
carry their own validator — a field cannot be declared without its
normalisation.

| Field | Rule |
| --- | --- |
| `first_name`, `last_name` | Trimmed, internal whitespace runs collapsed to one space |
| `username` | Trimmed, lower-cased, spaces become dots; must match `^[a-z0-9][a-z0-9._-]*$` |
| `email`, `personal_email` | Trimmed, lower-cased |
| `phone_number` | Trimmed; blank becomes `NULL`. Must match `^\+?[0-9][0-9 ()\-]{6,20}$` |
| `date_of_birth` | Not in the future; implied age between 14 and 100 |

The mobile pattern is deliberately permissive: it accepts the international
formats people actually type (`+91 98765 43210`, `020 7946 0958`,
`+1 (555) 123-4567`) while rejecting free text. Validating numbers properly needs
a library and a country context, neither of which this module has.

The age bounds catch the far more common slip than a future date: entering the
current year.

## 8. Passwords

| Rule | Value |
| --- | --- |
| Minimum length | 8 characters |
| Maximum | 72 bytes (bcrypt truncates beyond it) |
| Required | one uppercase, one lowercase, one digit, one special character |
| Storage | bcrypt, via `passlib`. Never plain text, never reversible |

One definition — `app.schemas.user.PasswordStr` — is shared by create, admin
reset, self-service change and the forgot-password flow, so the policy cannot
drift between them. The Zod schema on the client mirrors it; the server remains
the authority.

### Three ways a password changes

| Route | Who | Effect |
| --- | --- | --- |
| `POST /users/{id}/reset-password` | An administrator, for someone else | Sets the password. By default also sets `force_password_change` and revokes every session |
| `POST /auth/change-password` | A user, for themselves | Requires the current password. Revokes every session including the caller's |
| `POST /auth/reset-password` | Anyone holding a valid reset token | Single-use token. Revokes every session |

Both reset flags default to `true` because a reset performed in response to a
suspected compromise has to actually end it.

`force_password_change` is part of the user object, so it comes back on the very
next sign-in and the client can route straight to a change-password screen.
Setting a password — by any of
the three routes — clears the flag, resets the failed-attempt counter, lifts any
lockout, and invalidates any outstanding reset token.

## 9. Two audiences, two schemas

An administrator and a user editing themselves are different questions with
different answers, so they are different models and different routes.

```
UserCreate / UserUpdate   →  everything: names, username, official email,
                             organizational placement, status
ProfileUpdate             →  personal_email, phone_number, avatar_url
```

`ProfileUpdate` does not *filter out* administrative fields — it does not have
them. Combined with `extra="forbid"`, an attempt to send one is a `422` rather
than a field quietly dropped somewhere downstream.

That matters because there is **no RBAC yet**: every authenticated user can
currently reach the administrative routes. The schema split is the boundary that
holds regardless, and when roles land they guard those routes without changing
their shape.

`password` is absent from `UserUpdate` as well. Setting someone else's password
is a separate, separately audited operation, not a field on a general edit.

## 10. API

Eleven endpoints under `/api/v1/users`, all requiring
`Authorization: Bearer <token>`. Full request and response detail is in
[`API.md`](API.md#6-user-management).

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/users` | Paged directory: search, status, org filters, sorting |
| `POST` | `/users` | Create → `201` |
| `GET` | `/users/{id}` | One account, archived included |
| `PATCH` | `/users/{id}` | Partial update |
| `POST` | `/users/{id}/activate` | Restore sign-in |
| `POST` | `/users/{id}/deactivate` | Block sign-in, end sessions |
| `POST` | `/users/{id}/archive` | Soft delete |
| `POST` | `/users/{id}/restore` | Undo the archive |
| `POST` | `/users/{id}/reset-password` | Set a password on someone's behalf |
| `GET` | `/users/me` | The caller's own profile |
| `PATCH` | `/users/me` | Self-service update |

Search covers the staff code, username, both name parts, the composed full name,
both email fields and the mobile number. Live and archived accounts are never
mixed in one page.

Responses embed the resolved organizational names, not just the ids, so a list
row needs no extra request. The eight relationships are eager-loaded
(`lazy="joined"`) for the same reason — lazy loading them would be an N+1 per
row.

`GET /users/{id}` returns archived accounts, so a link from the archive list or a
stale bookmark resolves instead of 404ing confusingly.

## 11. Audit

Every action writes an `audit_logs` row capturing the action, entity type, record
id, timestamp, actor and request id.

```
user.created              user.deactivated       user.password.reset_by_admin
user.updated              user.archived          user.profile.updated
user.activated            user.restored
```

The password reset records *that* it happened, who did it, and the two flags —
never the password. `user.profile.updated` is distinct from `user.updated` so a
self-service change is legible as one in the trail.

A rejected write is **not** audited as a change: the request rolls back, so the
trail records only what actually happened.

## 12. Architecture

Clean Architecture throughout — routes → services → repositories → models — with
the request-scoped session as the unit of work.

### Backend

| Layer | File |
| --- | --- |
| Model | `app/models/user.py` |
| Migration | `alembic/versions/..._0003_user_management_extend_users.py` |
| Schemas | `app/schemas/user.py` |
| Repository | `app/repositories/user_repository.py` |
| Service | `app/services/user_service.py` |
| Routes | `app/api/v1/routes/users.py` |

`UserRepository` reuses the paging, search-escaping and archived-scoping helpers
the Organization module already had; `UserService` holds every guard in §5. Both
are constructed in `app/api/deps.py`, where the team repository and token service
are injected — the team repository for the linked-records check, the token
service for session revocation.

`UserService` takes both optionally, so the authentication flow, which needs only
`set_password`, is not forced to construct the whole directory dependency graph.

### The migration

Expand → backfill → contract, in one revision, because `users` already had rows
in every environment:

1. Create the sequence and add every column as nullable.
2. Backfill: split `full_name` on the first space into the two parts; derive
   usernames from email local parts, de-duplicated with `ROW_NUMBER()`; assign
   staff codes ordered by `created_at`; `setval` the sequence past the highest.
3. Contract: set `NOT NULL`, add the indexes, foreign keys and the gender check,
   and drop `full_name` and `job_title`.

A single-token existing name is deliberately duplicated into both parts rather
than left blank — it flags the row for correction instead of failing the
migration or hiding the person from a name search.

The downgrade recomposes `full_name` from the parts and drops the sequence, and
is exercised, not assumed.

### Frontend

```
src/features/users/
├── api/users.api.ts           one client
├── hooks/use-users.ts         data hooks + a lifecycle mutation factory
├── schemas/user.schemas.ts    Zod, mirroring the server rules
├── types/user.types.ts        re-exports the shared record type
└── components/
    ├── user-form.tsx          four sections, shared by create and edit
    ├── user-list-page.tsx
    ├── user-detail-page.tsx
    ├── user-form-page.tsx
    ├── profile-form.tsx
    └── reset-password-dialog.tsx
```

```
/users            directory
/users/new        create
/users/[id]       detail
/users/[id]/edit  edit
/profile          self-service
```

The record type lives in `src/types/user.ts`, not inside the feature, because
both `auth` and `users` need it and features must not import each other.

List state lives in the URL (`?q=`, `?view=`, `?sort=`, `?dir=`, `?page=`) via
the same hook the master screens use, so a filtered view can be bookmarked,
shared and restored by the back button.

The four lifecycle actions share one mutation factory, so cache invalidation and
the failure toast behave identically for all of them rather than being
re-implemented per action with slightly different bugs. The failure toast shows
the server's message verbatim: these actions are refused for specific, actionable
reasons, and a generic "something went wrong" would hide exactly the part the
administrator needs.

Optional fields send an explicit `null` when cleared. `undefined` is dropped by
`JSON.stringify`, which silently turns "clear this field" into "leave it alone".

### Reusable components

Added to `src/components/common/` because later modules need them:

| Component | Purpose |
| --- | --- |
| `UserAvatar` | Photo, or initials on a colour derived from the name |
| `UserIdentity` | Avatar plus name and a secondary line — one table cell |
| `ProfileCard` | The identity header on the detail and profile pages |
| `ActionMenu` | Data-driven row menu: an array of items with `hidden`, `disabled`, `destructive` and `separatorBefore` |

`ActionMenu` takes a list rather than children so a hidden or disabled action is
a property of the data, not a conditional rendered into JSX at each call site.

## 14. Deliberate limitations

- **No RBAC.** Every authenticated user can reach the administrative routes. The
  choke point is a single dependency (`get_current_user`), and the schema split
  in §9 already draws the line, so adding roles is additive.
- **No employee link.** `users` is the anchor an `employees` row will hang off;
  that table does not exist yet.
- **Placement is not validated as a tree** — see §2.
- **No bulk import or invitation email.** Accounts are created one at a time with
  a password set by the administrator. Both would sit on the existing service
  layer.
- **`avatar_url` is a URL, not an upload.** There is no file storage in the
  platform yet. Adding one changes how the field is populated, not what it is.
- **Organizational pickers load 100 active records each.** Fine for the expected
  volumes; a searchable async picker is the upgrade path.
- **Deactivation revokes sessions but does not notify the user.** There is no
  mail transport configured outside production.
