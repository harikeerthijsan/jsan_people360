# Database schema

## Workforce Planning (migration `0006_job_requisitions`)

`job_requisitions` stores manpower demand; `requisition_approvals` is the ordered approval chain; `requisition_attachments` links Document Vault records; `requisition_history` is append-only activity; and `notifications` stores in-app delivery. All use UUID keys and the shared audit/soft-delete columns.

## Document Vault (migration `0005_document_vault`)

The Document Vault adds `document_categories`, `document_types`, `documents`
and append-only `document_versions`. Documents use a polymorphic `(owner_type,
owner_id)` reference so future modules can reuse the vault. The current version
is denormalized onto `documents`; every stored version retains its checksum,
content metadata and opaque storage key. Expiry state is derived from
`expiry_date` at read time rather than stored.

PostgreSQL 14+. The schema is owned exclusively by Alembic; see
[`backend/alembic/README.md`](../backend/alembic/README.md) for the migration
workflow.

Current revision: **`0004_employee_master`** — *Employee master*.

| Revision | Adds |
| --- | --- |
| `0001_initial` | `users`, `refresh_tokens`, `audit_logs`, `app_settings` |
| `0002_org_masters` | `organizations`, `business_units`, `practices`, `departments`, `teams`, `designations`, `locations`, `employment_types`, `grades` |
| `0012_remove_practice_department` | Drops `practices` and `departments`; re-parents `teams` and `designations` onto `business_units` |

| `0004_employee_master` | `employees`, `employee_addresses`, `employee_bank_details`, `employee_identification`, `employee_employment_history` |

## 1. The audit contract

Every table in the platform carries the same seven columns. They are declared
once in `app/db/mixins.py` as `AuditableBase`, so a new model inherits the whole
contract.

| Column | Type | Null | Default | Purpose |
| --- | --- | --- | --- | --- |
| `id` | `uuid` | no | `gen_random_uuid()` | Primary key |
| `created_at` | `timestamptz` | no | `now()` | Row creation |
| `updated_at` | `timestamptz` | no | `now()` | Last modification |
| `created_by` | `uuid` | yes | — | FK → `users.id`, `ON DELETE SET NULL` |
| `updated_by` | `uuid` | yes | — | FK → `users.id`, `ON DELETE SET NULL` |
| `deleted_at` | `timestamptz` | yes | — | Soft delete marker; `NULL` = active |
| `deleted_by` | `uuid` | yes | — | FK → `users.id`, `ON DELETE SET NULL` |

**Why UUIDs.** Sequential integers leak volume ("how many employees does this
company have?") and make cross-environment data movement error-prone. UUIDs are
generated by PostgreSQL, so the application never has to round-trip for an id.

**Why soft delete.** HR records are subject to retention obligations that a
`DELETE` would violate. `BaseRepository` filters `deleted_at IS NULL` on every
read unless `include_deleted=True` is passed, so forgetting to filter is not a
failure mode.

**Why the audit columns are nullable.** System-initiated writes (seeding,
scheduled jobs) genuinely have no human actor. `ON DELETE SET NULL` means
removing a user never cascades into deleting the records they touched.

## 3. `users`

Authenticated principals **and** directory records of the platform. One table
serves both, and will later anchor `employees` — the reasoning is in
[`UserModule.md`](UserModule.md#1-one-table-three-jobs).

### Identity

| Column | Type | Null | Notes |
| --- | --- | --- | --- |
| `user_code` | `varchar(20)` | no | **Unique.** `USR-000001`, generated by the database. Never editable |
| `username` | `varchar(50)` | no | **Unique on `lower(username)`.** Sign-in handle |
| `first_name` | `varchar(100)` | no | |
| `last_name` | `varchar(100)` | no | `full_name` is derived from the pair, never stored |
| `email` | `varchar(320)` | no | **Unique.** Official address, stored lower-cased and trimmed; also a sign-in identifier |
| `personal_email` | `varchar(320)` | yes | The address that survives offboarding |
| `phone_number` | `varchar(32)` | yes | Mobile number |
| `avatar_url` | `varchar(1024)` | yes | Profile photo |
| `gender` | `varchar(20)` | yes | CHECK: `male`, `female`, `other`, `prefer_not_to_say` |
| `date_of_birth` | `date` | yes | |

### The staff code sequence

```sql
CREATE SEQUENCE users_user_code_seq;

ALTER TABLE users ALTER COLUMN user_code
  SET DEFAULT 'USR-' || lpad(nextval('users_user_code_seq')::text, 6, '0');
```

A column default rather than application code. Two concurrent inserts computing
`max(user_code) + 1` would read the same maximum and produce the same code; the
unique index would then reject one of them for a reason the user cannot act on.

### Organizational placement

Eight nullable foreign keys, all `ON DELETE RESTRICT`, each with its own index:

| Column | References |
| --- | --- |
| `business_unit_id` | `business_units.id` |
| `team_id` | `teams.id` |
| `designation_id` | `designations.id` |
| `grade_id` | `grades.id` |
| `location_id` | `locations.id` |
| `employment_type_id` | `employment_types.id` |
| `joining_date` | `date`, not a reference |

**Nullable** because a user can legitimately exist before the org tree does: the
bootstrap administrator is created against an empty database.

**`RESTRICT`** because master records are archived, never deleted. A hard delete
that silently unassigned every user is not a recovery path.

### Credentials

| Column | Type | Null | Notes |
| --- | --- | --- | --- |
| `hashed_password` | `varchar(255)` | no | bcrypt. **Never** leaves the database — `UserRead` omits it |
| `password_changed_at` | `timestamptz` | yes | Supports future password-age policy |
| `force_password_change` | `boolean` | no | Default `false`. Set by an administrator reset; the client must collect a new password |
| `password_reset_token_hash` | `varchar(64)` | yes | SHA-256 digest of the outstanding reset token |
| `password_reset_expires_at` | `timestamptz` | yes | Reset token expiry |

Reset tokens live on `users` rather than in their own table, because a user can
have at most one outstanding reset at a time. A separate table would add a join
and an orphan-cleanup problem for no gain.

### Status

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `is_active` | `boolean` | no | `true` | `false` blocks sign-in with 403 and revokes every session |
| `is_superuser` | `boolean` | no | `false` | **Reserved for RBAC. Not enforced yet** |
| `email_verified_at` | `timestamptz` | yes | | Reserved for email verification |

`is_active` is presented to API clients as `status: active | inactive`, matching
the master-data screens. There is no `status` column — the projection happens in
the schema layer so the two cannot disagree.

### Sign-in telemetry and lockout

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `last_login_at` | `timestamptz` | yes | | Last successful sign-in |
| `last_login_ip` | `varchar(45)` | yes | | IPv6-sized |
| `failed_login_attempts` | `integer` | no | `0` | Reset on success |
| `locked_until` | `timestamptz` | yes | | Set after `MAX_FAILED_LOGIN_ATTEMPTS` |

### Indexes

| Name | Columns | Unique |
| --- | --- | --- |
| `pk_users` | `id` | PK |
| `ix_users_user_code` | `user_code` | yes |
| `ix_users_email` | `email` | yes |
| `uq_users_username_lower` | `lower(username)` | yes |
| `ix_users_username` | `username` | no |
| `ix_users_name` | `first_name, last_name` | no |
| `ix_users_is_active_deleted_at` | `is_active, deleted_at` | no |
| `ix_users_password_reset_token_hash` | `password_reset_token_hash` | no |
| `ix_users_deleted_at` | `deleted_at` | no |
| `ix_users_<ref>_id` | one per organizational reference (8) | no |

The email index is unique across *all* rows, including soft-deleted ones. An
address stays reserved after deletion, so a re-created account cannot be confused
with its predecessor in the audit trail. The same holds for the username.

Username uniqueness is on `lower(username)` because a plain `UNIQUE` would accept
both `J.Doe` and `j.doe` — the same handle as two accounts, which is a phishing
surface. Email needs no equivalent: it is lower-cased before it is stored.

### Migration `0003_user_management`

`users` already had rows in every environment, so the revision is
expand → backfill → contract in one step:

1. **Expand** — create the sequence, add every column nullable.
2. **Backfill** — split `full_name` on the first space into the two parts;
   derive usernames from email local parts, de-duplicated with `ROW_NUMBER()`;
   assign staff codes ordered by `created_at`; `setval` the sequence past the
   highest.
3. **Contract** — set `NOT NULL`, add the indexes, foreign keys and the gender
   CHECK, then drop `full_name` and `job_title`.

`full_name` became derived, and `job_title` was free text superseded by
`designation_id`. A single-token existing name is deliberately duplicated into
both parts rather than left blank: it flags the row for correction instead of
failing the migration or hiding the person from a name search.

The downgrade recomposes `full_name` from the parts and drops the sequence, and
is exercised rather than assumed.

## 4. `refresh_tokens`

Rotating refresh tokens backing authenticated sessions.

| Column | Type | Null | Notes |
| --- | --- | --- | --- |
| `user_id` | `uuid` | no | FK → `users.id`, **`ON DELETE CASCADE`** |
| `token_hash` | `varchar(64)` | no | **Unique.** SHA-256 digest; the raw token is never stored |
| `expires_at` | `timestamptz` | no | Absolute expiry |
| `revoked_at` | `timestamptz` | yes | Set on rotation, logout or theft detection |
| `revoked_reason` | `varchar(100)` | yes | `rotated`, `logout`, `logout_all`, `password_reset`, `password_changed`, `refresh_token_reuse_detected`, `account_unavailable` |
| `replaced_by_id` | `uuid` | yes | FK → `refresh_tokens.id`, `ON DELETE SET NULL`. Forms the rotation chain |
| `user_agent` | `varchar(512)` | yes | Session provenance |
| `ip_address` | `varchar(45)` | yes | Session provenance |

### Indexes

| Name | Columns | Unique |
| --- | --- | --- |
| `pk_refresh_tokens` | `id` | PK |
| `ix_refresh_tokens_token_hash` | `token_hash` | yes |
| `ix_refresh_tokens_user_id` | `user_id` | no |
| `ix_refresh_tokens_user_id_expires_at` | `user_id, expires_at` | no |
| `ix_refresh_tokens_deleted_at` | `deleted_at` | no |

### Notes

- `CASCADE` here — not `SET NULL` — because a token without a user is meaningless
  and would be a security liability.
- Revoked rows are **kept**. They are how replay is detected: a token whose row
  is already revoked proves two parties hold the same secret.
- `purge_expired()` soft-deletes rows past expiry. Nothing schedules it yet.

### Platform actions

| Action | Emitted when |
| --- | --- |
| `auth.login.succeeded` | Successful sign-in |
| `auth.login.failed` | Unknown email or wrong password |
| `auth.login.blocked` | Account locked or deactivated |
| `auth.logout` | Sign-out (single or all sessions) |
| `auth.token.refreshed` | Refresh token rotated |
| `auth.token.reuse_detected` | Revoked refresh token replayed |
| `auth.password.reset_requested` | Reset link requested |

| `auth.password.changed` | Password changed while signed in |
| `user.created` / `user.updated` / `user.deleted` | Account lifecycle |
| `user.activated` / `user.deactivated` | Sign-in enabled or blocked |
| `user.archived` / `user.restored` | Soft delete and its undo |
| `user.password.reset_by_admin` | An administrator set someone else's password |
| `user.profile.updated` | A user changed their own profile |
| `organization.<entity>.<verb>` | Master-data lifecycle — nine entities × four verbs |
| `employee.created` / `updated` / `archived` / `restored` | Employee record lifecycle |

| `employee.team.transferred` / `designation.changed` / `manager.changed` / `location.changed` | Placement changes |
| `employee.bank.updated` / `identification.updated` | Sensitive records changed — the fields, never the values |
| `employee.sensitive.viewed` | Unmasked bank or identity details were read |

| `settings.updated` | Runtime setting changed |

(`"employee.created"`); the enum fixes only platform-level events.

### Notes

- `actor_email` is denormalised deliberately. `ON DELETE SET NULL` on `actor_id`
  would otherwise erase who performed an action — exactly the record an audit
  trail exists to keep.
- `context` uses `jsonb`, not `json`, so it is indexable and stored parsed.
- `AuditService.record()` never raises. A failure to write the trail must not
  fail the operation it describes; it is logged at ERROR level instead.
- The table carries the soft-delete columns for consistency, but nothing in the
  application deletes from it.

## 7. Organization master data

Nine tables added by `0002_org_masters`. Behaviour and business rules are
documented in [`OrganizationModule.md`](OrganizationModule.md); this section is
the schema.

### Shared master columns

Beyond the audit contract in §1, every master table carries:

| Column | Type | Null | Notes |
| --- | --- | --- | --- |
| `name` | `varchar(150)` | no | Trimmed and whitespace-collapsed before insert |
| `description` | `text` | yes | Blank is stored as `NULL`, never `''` |
| `status` | `varchar(20)` | no | `active` \| `inactive`, default `active`, CHECK constrained |
| `code` | `varchar(50)` | no | All masters except `teams` and `organizations` |

**`status` is not soft delete.** `status` is a business flag; `deleted_at` is the
archive. A record can be inactive and live, or active and archived.

### Case-insensitive uniqueness

Uniqueness is enforced with **functional unique indexes on `lower(column)`**:

```sql
CREATE UNIQUE INDEX uq_designations_code_lower ON designations (lower(code));
CREATE UNIQUE INDEX uq_designations_business_unit_id_name_lower
    ON designations (business_unit_id, lower(name));
```

A plain `UNIQUE` would accept both `GIS` and `gis` — a genuine data-quality bug
in records other modules reference by name.

These indexes cover **every row, archived included**, so an archived record keeps
its name and code reserved. The service detects that case and returns a message
telling the user to restore the record rather than a bare integrity error.

### Tables

| Table | Parent (FK) | Unique code | Unique name | Extra columns |
| --- | --- | --- | --- | --- |
| `organizations` | — | — | global | `legal_name`, `registration_number` (unique), `gst_number`, `pan_number`, `logo_url`, `website`, `timezone`, `currency`, `address_line1/2`, `city`, `state`, `country`, `postal_code` |
| `business_units` | — | global | global | — |
| `teams` | `business_units.id`, `users.id` (manager) | — | per business unit | `manager_id` |
| `designations` | `business_units.id` | global | per business unit | `level` (int, CHECK ≥ 1) |
| `locations` | — | global | global | `country`, `state`, `city`, `address`, `timezone` |
| `employment_types` | — | global | global | — |
| `grades` | — | global | global | `level` (int, CHECK ≥ 1) |

### Foreign key behaviour

| Relationship | `ON DELETE` | Why |
| --- | --- | --- |
| Hierarchy parents (`teams → business_units`, and so on) | `RESTRICT` | Archiving is the supported way to retire a record. A hard delete that orphaned children would corrupt the tree, so the database refuses it outright |
| `teams.manager_id → users.id` | `SET NULL` | A team survives its manager leaving |
| Audit columns (`created_by`, `updated_by`, `deleted_by`) | `SET NULL` | Removing a user must not cascade into the records they touched |

`teams.manager_id` points at `users` because the Employee module does not exist
yet. It is already a nullable UUID foreign key, so repointing it at `employees`
later is a migration rather than a redesign.

### Indexes

Every master has, in addition to the unique indexes above:

- `ix_<table>_name`, `ix_<table>_status`, `ix_<table>_deleted_at` — the columns
  every list query filters or sorts on
- `ix_<table>_code` where a code exists
- An index on each foreign key
- `ix_designations_level`, `ix_grades_level`
- `ix_locations_city`, `ix_locations_country`

### `employees`

| Group | Columns |
| --- | --- |
| Identity | `employee_code` (unique, sequence-generated), `user_id` (unique, nullable) |
| Personal | `first_name`, `last_name`, `gender`, `date_of_birth`, `blood_group`, `marital_status`, `nationality`, `photo_url` |
| Contact | `personal_email`, `mobile_number`, `alternate_number`, `emergency_contact_name`, `emergency_contact_number`, `emergency_contact_relationship` |
| Official | `official_email` (unique on `lower(...)`), `official_mobile`, `extension_number`, `work_mode` |
| Employment | `joining_date` (NOT NULL), `confirmation_date`, `employment_status`, and nine references |
| Compensation | `ctc` (`numeric(14,2)`), `salary_grade_id` |
| Reserved | `shift_id` |

**Why `numeric`, not `float`.** Money must not round. A binary float cannot
represent 1450000.10 exactly, and the error compounds through every payroll
calculation that will later read this column.

**The employee-code sequence**

```sql
CREATE SEQUENCE employees_employee_code_seq;

ALTER TABLE employees ALTER COLUMN employee_code
  SET DEFAULT 'EMP-' || lpad(nextval('employees_employee_code_seq')::text, 6, '0');
```

A column default rather than application code: two concurrent inserts computing
`max(employee_code) + 1` would read the same maximum and produce the same code.

**`shift_id`** is a nullable UUID with **no foreign key**, reserved for the Shift
master that does not exist yet. It is absent from every write schema, so nothing
can populate it until there is a table to validate it against. The Shift module
adds the constraint; it does not add the column.

**CHECK constraints** restrict `gender`, `blood_group`, `marital_status`,
`employment_status` and `work_mode` to their known values, keep `ctc` non-negative,
and stop an employee reporting to themselves. Every enum is a `varchar` with a
CHECK rather than a PostgreSQL `ENUM` type: adding a value to a native enum needs
`ALTER TYPE`, which cannot be rolled back inside a transaction and makes an
otherwise trivial migration irreversible.

The deeper reporting cycle — A ↦ B ↦ A — cannot be expressed as a CHECK and is
enforced in the service with a recursive CTE.

### The satellite tables

All three use `ON DELETE CASCADE` from `employee_id`: none is meaningful without
the employee it belongs to.

Uniqueness is enforced with **partial unique indexes on the live rows**
(`WHERE deleted_at IS NULL`), so an archived row does not block re-entry:

```sql
CREATE UNIQUE INDEX uq_employee_addresses_employee_id_type
    ON employee_addresses (employee_id, address_type) WHERE deleted_at IS NULL;

CREATE UNIQUE INDEX uq_employee_identification_aadhaar
    ON employee_identification (upper(aadhaar_number))
    WHERE aadhaar_number IS NOT NULL AND deleted_at IS NULL;
```

Every statutory identifier — Aadhaar, PAN, passport, UAN, PF, ESI — gets one of
these. Partial on `IS NOT NULL` because most are optional, and a plain unique
index would carry every NULL row for nothing.

**`employee_bank_details` and `employee_identification` are separate tables so
that reading an employee does not read them.** That is what keeps account numbers
and Aadhaar out of exports, list queries and log lines by default. Their
`__repr__` omits every sensitive column, because `repr()` ends up in tracebacks.

Both store plain text. What protects them is the table split, masking in the read
models, a single audited reveal endpoint, and exclusion from exports —
**not encryption**. See
[`EmployeeModule.md` §8](EmployeeModule.md#8-sensitive-data).

### `employee_employment_history`

| Column | Purpose |
| --- | --- |
| `change_type` | What prompted the row; CHECK constrained |
| `effective_date` | When the change takes effect — not when it was entered |
| `team_id`, `designation_id`, `grade_id`, `work_location_id`, `reporting_manager_id`, `employment_status` | The state **after** the change |
| `summary` | Human-readable account, composed at write time and frozen |
| `reason`, `notes` | Why, as entered |

A snapshot rather than a diff: given a date, this answers "which team were
they in?", which is exactly what attendance, payroll and performance will need to
ask about periods that have already closed.

`summary` is frozen at write time so the timeline still reads correctly after one
of the master records is renamed.

The table is **append-only by policy** — no endpoint updates or deletes a row —
and by constraint: `reporting_manager_id` is `RESTRICT`, so an employee who
appears in someone else's history cannot be hard-deleted out of it.

Indexed on `(employee_id, effective_date)`, which is the query the profile
timeline issues.

### Foreign key behaviour

| Relationship | `ON DELETE` | Why |
| --- | --- | --- |
| The nine organizational references | `RESTRICT` | Masters are archived, never deleted; a hard delete that silently unassigned every employee is not a recovery path |
| `employees.user_id → users.id` | `RESTRICT` | Removing an account must not orphan the employment record |
| `employees.reporting_manager_id → employees.id` | `RESTRICT` | Self-referential |
| Satellite `employee_id` | `CASCADE` | Meaningless without their employee |
| History `reporting_manager_id` | `RESTRICT` | History must not be hollowed out |

## 9. Conventions for new tables

1. Inherit `Base` and `AuditableBase` — the audit contract is not optional.
2. Table names are `snake_case` and plural.
3. Every foreign key states its `ondelete` explicitly. Choose deliberately:
   `CASCADE` when the child is meaningless alone, `SET NULL` when the record
   should outlive the reference, `RESTRICT` when deletion should be refused.
4. Timestamps are always `timestamptz`. Never `timestamp`.
5. Index every foreign key and every column used for filtering.
6. Structured payloads use `jsonb`, not `json` or `text`.
7. Constraints use the metadata naming convention — never an anonymous
   constraint, which cannot be dropped reliably in a downgrade.
8. Add the table to `app/models/__init__.py` so Alembic autogenerate can see it.

Verify models and schema agree at any time:

```bash
cd backend
alembic check        # exits non-zero if they have drifted
```

72-permission catalogue and the eight system roles, grants Super Admin to
existing superusers so the first deploy cannot lock out the only administrator,
